# Работа над SyncSyncAV

[English](AGENTS.md) · [Руководство по сборке](engine/README.ru.md)

## Код и проверки

- Интерфейс Windows и логика синхронизации находятся в `source/`. Названия команд и подсказки редактируйте для обоих языков в `source/Strings.xml`. Если меняется видимое пользователю действие, обновите соответствующий раздел обоих README.
- Протокол связи проверяйте с обеих сторон. Клиент находится в `source/BridgeClient.cs`, мост VirtualDub2 — в `engine/bridge/`. Закреплённые ревизии VirtualDub2 и модуля ввода перечислены в `engine/upstream.json`. Изменения стороннего кода храните в `engine/patches/` вместе с подходящей ревизией. Сохраняйте лицензии и указания авторства.
- Для быстрой проверки оболочки выполните `./source/build.ps1` из корня репозитория. Команда `./tests/test.ps1` проверяет сессию и обмен с движком. Для правок открытия файлов, выбора плейлиста или управления панелями выполните `python tests/file_drop.py <папка-собранного-приложения>`. Тесту нужна собранная программа вместе с папкой `Engine`. Проверяйте обе панели и обе локализации, если изменение их затрагивает.

## Git и личные данные

В новом клоне настройте автора для этого проекта и включите его хуки.

```powershell
git config --local user.name "SyncSyncAV contributors"
git config --local user.email project@localhost.invalid
git config --local core.hooksPath .githooks
```

Перед коммитом посмотрите подготовленный diff, перед отправкой — список исходящих коммитов. Хуки проверяют личные данные и авторство, упаковщик — историю и содержимое ZIP. Личные адреса и пути профиля, ISO фильмов, старые сборки, архив прежней истории, пользовательские настройки и журналы сеансов остаются на рабочей машине. Для воспроизводимых тестов используйте синтетические файлы из `tests/`.

## Работа с GitHub

- Основная ветка — `main`. Если пользователь попросил черновик, покажите его до отправки изменений на GitHub. Отправляйте ветки, создавайте теги и публикуйте релизы в пределах текущего поручения.
- Локальную сборку используйте для разработки. Кандидат в релиз собирает **Build Windows ZIPs** на GitHub Actions. Для выпуска укажите ID успешной сборки из `main` в **Release Windows ZIPs**. По умолчанию этот workflow проверяет оба ZIP. Включайте **Publish** по поручению опубликовать релиз.
- Оба архива переходят из Actions в Release на раннере GitHub. После публикации сверьте коммит тега, имена, размеры и SHA-256 обоих вложений с исходной сборкой. Для проверки публичных ссылок используйте анонимные запросы HTTP HEAD. Скачивать ZIP на рабочую машину для этой проверки не требуется.
